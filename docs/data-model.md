# Data model

Applies from turn 2. Schema source of truth: `core/migrations/` (sqlx, forward-only, embedded in the binary). This page explains the design; if they disagree, the migrations win.

## Where things live
| What | Where | Notes |
|---|---|---|
| Prose (books, chapters, scenes) | Markdown files in one Git repository per book | The only copy of the text. Every save is a Git commit. |
| Structure, identifiers, story graph, canon ledger | SQLite file (`pero.db`) | Never the only copy of prose. The structure tables can be rebuilt by re-reading the repositories; the story graph and canon ledger are authored data and are backed up with the database. |
| Server settings | `/etc/pero/server.toml` | Outside the repository. |

Layout on the server: `<data_dir>/pero.db` and `<data_dir>/books/<book-id>/` (the repository). `data_dir` is an optional key in `/etc/pero/server.toml`; without it the manuscript API is not mounted.

## Identifiers
- Short random text IDs generated by the server (40 random bits, Crockford base32, lowercase), never reused, never derived from content or position.
- Books, chapters, scenes, entities, relationships, events and facts carry a type prefix (`bk_`, `ch_`, `sc_`, `en_`, `rl_`, `ev_`, `ft_`).
- Passage IDs are the bare 8-character value; the same value is the marker in the Markdown (see below).
- IDs are validated in the application, not by `CHECK` constraints, so the format can change without a table rebuild.
- Timestamps are UTC ISO 8601 text (`2026-10-28T09:10:00.000Z`).

## Passages (decided with the owner on 2026-10-28)
- **Granularity:** one paragraph (a block separated by a blank line). In Russian typography each dialogue line starting with «—» is its own paragraph and so its own passage. Headings and scene breaks are not passages.
- **Marker in Markdown:** a hidden comment at the end of the paragraph, `<!-- p:k7m2x9qa -->`. Invisible when rendered; it moves with the paragraph when text is edited or reordered. The API exposes passages as structured `{id, text}` items, so clients never edit markers by hand.
- **Edits:** changing the words keeps the ID. Splitting keeps the ID on the first part and gives the new part a new ID. Merging keeps the first ID and tombstones the other with `merged_into`. Moving a paragraph to another scene keeps the ID (`scene_id` changes).
- **Never deleted:** a removed or merged passage stays in `passages` as a tombstone (`status = 'removed'`, `removed_at`), so evidence links always resolve and the facts that cite it can be flagged instead of silently losing their evidence. A `DELETE` on a cited passage is refused by a foreign key.
- **Text hash:** SHA-256 (hex) of the normalised paragraph text (stored in `text_hash`); evidence stores the hash at the time of citing, so an edited passage marks its evidence out of date.
- **Normalisation** (import and save): line endings to `\n`, trailing spaces removed, one blank line between paragraphs, one final newline. Unicode is not changed: no NFC conversion, «ёлочки», dashes and «ё» are untouched.

## Book repository layout (manuscript store, part 2)
```
books/<book-id>/
  book.toml                        id, title, language
  chapters/001-glava-pervaya/
    chapter.toml                   id, title
    001-utro.md                    one scene
    002-vecher.md
```
- Order is the numeric prefix. Reordering is a rename (Git records it as a move) in one commit; IDs live inside the files and never change. Folder and file names are ASCII slugs made from the title when created (Cyrillic transliterated) and do not follow later title changes.
- A scene file is a TOML block between `+++` lines (`id`, `title`, `language`, optional `pov`, `date`, `location`), then paragraphs separated by blank lines, each ending with ` <!-- p:ID -->`. A paragraph may span several lines. Headings and scene breaks are not part of a scene file; chapter and scene titles live in the TOML.
- **One commit per change**, made under a per-book lock: the working tree must be clean (otherwise the change is refused with `repository_dirty` and nothing is touched), the change is written, committed, and the index is rebuilt from the repository. A failure before the commit rolls the change back. A save that changes nothing makes no commit. Commit authors are the acting device (`api` until device authentication exists).
- **Saving a scene** sends the whole scene and the `base_revision` it was read at (SHA-256 of the file). If the file changed since, the answer is 409 `revision_conflict` carrying the current scene; there is no automatic merge. Paragraphs that keep their `id` keep their identity whatever happened to their text or position; paragraphs without `id` are new; paragraphs left out are removed (tombstoned). `merged` names which staying passage absorbed a removed one. An `id` of a removed passage may be sent again (undo). An `id` that is still active in another scene is refused: remove it there first, then claim it.
- Scene fields (`title`, `language`, `pov`, `date`, `location`) are replaced as a whole; empty values are dropped.
- **Paragraph rules:** no blank line inside, not empty, not starting with `#`, not a scene-break line (`***`, `---`, `___`), no passage marker inside the text.
- **Rebuilding the index:** `POST /api/v1/books/{id}/reindex` re-reads the repository and fixes the SQLite index (also done after every change). Paragraphs that were added by hand have no marker; they are reported as `unmarked_paragraphs` and get an ID on the next save from Pero.

## API (`/api/v1`, JSON; no login yet, so not mounted unless `data_dir` is set)
| Method and path | Purpose |
|---|---|
| `GET`, `POST /books` | list; create `{title, language}` |
| `GET`, `PATCH /books/{id}` | read; rename `{title}` |
| `GET`, `POST /books/{id}/chapters` | list; create `{title, position?}` |
| `PUT /books/{id}/chapters/order` | `{ids}`: every chapter once, in the new order |
| `GET`, `PATCH /chapters/{id}` | read; rename |
| `GET`, `POST /chapters/{id}/scenes` | list; create `{title?, language?, pov?, date?, location?, position?}` |
| `PUT /chapters/{id}/scenes/order` | `{ids}` |
| `GET /scenes/{id}` | scene with `passages` `[{id, text}]` and `revision` |
| `PUT /scenes/{id}` | save `{base_revision, fields, passages: [{id?, text}], merged?: [{from, into}]}` → `{scene, commit}` |
| `POST /books/import` | import `{title, language, mode?, files: [{name, content}]}` as one commit (up to 16 MiB); 201 with `{book, chapters, scenes, passages, titles_from_filename}` |
| `GET /books/{id}/export` | every chapter as canonical Markdown `{files: [{name, content}]}` |
| `POST /books/{id}/reindex` | rebuild the index |

Errors are `{"error": {"code", "message"}}`: 404 `not_found`, 422 `invalid` (also for unknown fields) or `import_rejected` (with `issues: [{file, line, message}]`), 409 `revision_conflict` (with `current`) or `repository_dirty`, 500 `internal` (details only in the server log). Malformed JSON gets axum's plain-text 4xx.

## Import (part 3)
One Markdown file is one chapter; the files are read in natural name order (`2.md` before `10.md`) and become one new book in **one commit**. Either every file is understood or nothing is imported: the refusal lists up to 50 problems as file, line and message (never the text itself).

| In the file | Becomes |
|---|---|
| `# Title` (first in the file) | chapter title; without it, the title is made from the file name (leading digits and `_`/`-` dropped) and the file is listed in `titles_from_filename` |
| `## Title` | a scene with that title |
| `* * *`, `***`, `---`, `___` (blank lines around) | a scene break: the next paragraphs start an untitled scene. Breaks with no text before them are ignored |
| any other text | passages. `mode = "blank_line"` (default): a paragraph is a block of lines between blank lines. `mode = "line"`: every non-empty line is a passage (for text exported from word processors, where paragraphs are single lines) |
| `###` or other `#` forms, a heading or break glued to text without blank lines, a second `# ` heading, a passage marker inside the text, an empty heading | refused, with file and line |

Normalisation (import and the check): CR/LF and BOM to LF, trailing spaces removed, runs of blank lines collapsed, scene-break spellings to `* * *`, one final newline. **Words, punctuation and Unicode are never changed** (no NFC, «ёлочки», dashes and «ё» untouched).

**Round trip and the check.** `GET /books/{id}/export` writes each chapter back as canonical Markdown: `# Title`, `## Scene title` for titled scenes, `* * *` between untitled ones, paragraphs separated by blank lines. Two levels of proof:
1. *No text lost* (must pass): the characters of the original, ignoring whitespace, scene-break lines and heading marks, are identical to those of the export. This catches any dropped, duplicated, reordered or altered word and is independent of the splitting rules.
2. *Byte-identical to the normalised original* (reported): true for files that already follow the rules above. A file can differ only in notation (for example consecutive breaks, a break right before a `##` heading, single-line paragraphs in `line` mode); the report says which file and the first differing line.

**Checking your own chapters offline.** `pero-server check-import DIR [--mode blank-line|line] [--language ru|en]` imports the `*.md` files of DIR into a throw-away store, exports them again and prints the counts and both results. It prints only counts, file names and line numbers, never text, and removes its temporary folder; exit status 1 on a refusal or if any text differs. It also says when many paragraphs span 8 or more lines (a sign that `--mode line` is needed).

Speed: about 0.4 ms per passage (2000 passages in 1.7 s; the per-passage ID check and the index rebuild dominate); a 10 000-paragraph novel imports in a few seconds.

## Story graph API (part 4)
SQLite only, no Git: the graph is authored structure kept in the database (back it up with the database). Everything is scoped to one book; an entity, scene or place from another book is refused. Bodies are strict: unknown fields are a 422.

| Method and path | Purpose |
|---|---|
| `POST /books/{id}/entities` | create `{kind, name, description?, aliases?}`; `kind` is `character`, `place` or `organization` |
| `GET /books/{id}/entities[?kind=]` | list, ordered by kind then name ignoring case (Cyrillic too) |
| `GET`, `PATCH`, `DELETE /entities/{id}` | read; change `{name?, description?, aliases?}` (aliases are replaced as a whole; the kind never changes); delete `[?cascade=true]` |
| `POST /books/{id}/relationships` | create `{from_entity_id, to_entity_id, kind, directed?, description?}` (`directed` defaults to true) |
| `GET /books/{id}/relationships[?entity=]` | list; with `entity`, those touching it at either end |
| `GET`, `PATCH`, `DELETE /relationships/{id}` | read; change `{kind?, directed?, description?}` (the two entities never change: delete and create instead); delete |
| `POST /books/{id}/events` | create `{title, description?, when_text?, sort_order?, scene_id?, place_id?, participants?: [{entity_id, role?}]}` |
| `GET /books/{id}/events[?entity=]` | list in timeline order (`sort_order`, then id); with `entity`, those it takes part in |
| `GET`, `PATCH`, `DELETE /events/{id}` | read; change any field (absent keeps, `null` clears `when_text`, `scene_id`, `place_id`; `participants` replaces the list); delete |

Rules:
- **Entities:** name 1 to 300 characters on one line; description up to 5000 characters (line breaks allowed); up to 50 aliases, each 1 to 300 characters, different from each other and from the name. Two entities may share a name (two characters called Anna are legitimate).
- **Relationships:** two different entities of the book; `kind` is free text up to 100 characters ("sister of", "serves in"). The same relationship twice is refused with 409 `already_exists`: same pair, same kind, same direction, and an undirected one counts in both directions. "A loves B" and "B loves A" are two different directed relationships and are both allowed.
- **Events:** `when_text` is the date as the author writes it (fictional calendars are fine); `sort_order` is the author's order on the timeline, defaulting to 10 after the last event of the book; `place_id` must be a place; `scene_id` a scene of the same book; each participant at most once, up to 200, role up to 100 characters.
- **Deleting an entity** that is still used (relationships, event participations, event places) is refused with 409 `in_use`; with `?cascade=true` its relationships and participations are removed and place references cleared. Canon facts about an entity always block the deletion, cascade or not (the author decides about canon first, part 5).
- Deleting a relationship or an event never affects anything else; an event's participations go with it.
- Query strings accept only plain ASCII values (kinds, IDs, `true`/`false`) and only the documented keys; there is no server-side name search (the client filters the list; books are small).
- Text is stored exactly as sent: no Unicode normalisation, «ёлочки», dashes, «ё» and NBSP survive.

## Canon ledger API (part 5)
SQLite only. A fact is a statement about the story with a status, evidence passages and a status history. Facts are never deleted: a fact that turns out wrong is rejected and stays in the history.

| Method and path | Purpose |
|---|---|
| `POST /books/{id}/facts` | create `{text, entity_id?, origin?, status?, source_ref?, evidence?: [{passage_id}]}` |
| `GET /books/{id}/facts[?status=&entity=&passage=&origin=&stale=]` | list; filters combine with AND; `entity` and `passage` give "facts about this entity" and "facts citing this passage" |
| `GET`, `PATCH /facts/{id}` | read (with evidence); edit `{text?, entity_id?, source_ref?}` (`null` clears the last two); the status is not editable here |
| `POST /facts/{id}/approve`, `/reject`, `/reopen` | change the status; optional body `{"reason"}` (or no body) |
| `PUT /facts/{id}/evidence` | `{evidence: [{passage_id}]}` replaces the citations with fresh ones and clears the stale flag |
| `GET /facts/{id}/history` | every status change: from, to, who, why, when |
| `GET /passages/{id}` | index information of a passage: scene, position, `active` or `removed`, `merged_into` (the text itself is read from the scene) |

**Statuses:** `explicit` (stated in the text), `author_approved`, `ai_hypothesis`, `rejected` (a refused hypothesis or a retracted fact).

**How a fact starts** (`origin` is `author` by default):
| Origin | Allowed starting status | Evidence |
|---|---|---|
| `author` | `author_approved` (default) or `explicit`; entering a fact is the author's explicit act, so approval is recorded at once | required for `explicit`, optional for `author_approved` (backstory not yet in the text) |
| `ai` | only `ai_hypothesis`; asking for anything else is refused | at least one passage |
| `import` | only `explicit` | at least one passage |

**The approval rule.** An AI hypothesis becomes canon only through `approve`, an explicit act that records who and when (`approved_by`, `approved_at`). Every other route is closed: creation with another status is refused, the approval fields cannot be sent, `PATCH` has no status, and the database itself refuses `author_approved` without an approval record.

**Status changes:**
| Call | From | To |
|---|---|---|
| `approve` | `ai_hypothesis`, `rejected` | `author_approved` |
| `reject` | any status except `rejected` | `rejected` |
| `reopen` | `author_approved`, `rejected`, only for facts that came from AI | `ai_hypothesis` (approval record cleared) |

Anything else is 409 `invalid_transition`. Each change adds a history row, so a mistaken approval is reversible and auditable. Explicit facts need no approval.

**Evidence and stale facts.** Evidence cites passages that exist in the same book and are still active, and remembers the passage text hash at citing time. Whenever the manuscript index changes (a save, a reorder, a reindex), every fact that cites a passage that was **removed**, **merged into another** or **edited** is flagged `stale` with a reason, never deleted; the evidence entries show which passage is the problem (`passage_status`, `changed`). A removal or merge takes precedence over an earlier "edited" reason. The flag clears when the author re-cites with `PUT /facts/{id}/evidence`. Approving a stale fact is allowed (it is the author's call) and keeps the flag. Edits to other paragraphs, additions and reordering flag nothing.

**Actor.** Until device authentication exists (part 6) every change is recorded as `api`; AI facts record `ai:<source_ref>`.

## Known gaps in this part
- Import supports only the rules above (one file per chapter, `#`/`##` headings, plain paragraphs). Block quotes, lists, tables, images and deeper headings are kept as paragraph text if they sit inside a paragraph, but a line that starts a block with `#` is refused. Whether the owner's real chapters fit is decided by running `check-import` on them.
- Import creates a new book each time; importing again into an existing book is not supported.
- The story graph has no edit history or undo; it changes in place.
- Bulk approval and bulk rejection of facts (turn 7) are not here; each fact is approved one call at a time. A passage that comes back (undo) does not clear the stale flags it caused; the author re-cites to clear them.
- Deleting chapters, scenes or books is not implemented; a file deleted by hand leaves a stale index row until the delete operation exists.
- A paragraph moves between scenes in two saves (remove, then claim), not atomically.
- The index is rebuilt for the whole book after each change; fine for novel-sized books, to be optimised if it shows.
- `chapters.path` in the index is the chapter's folder (`chapters/001-slug`), not a file.

## Tables

### Manuscript index (`0001_manuscript.sql`)
| Table | Purpose | Key columns |
|---|---|---|
| `books` | One per book | `title`, `language` (`ru`/`en`), `head_commit` (Git commit the index reflects) |
| `chapters` | Ordered chapters | `book_id`, `position`, `title`, `path` (repository-relative) |
| `scenes` | Ordered scenes in a chapter | `chapter_id`, `position`, `path`, `language`, front-matter copies `pov`, `story_date`, `location` |
| `passages` | Paragraph-level passages incl. tombstones | `scene_id`, `position`, `text_hash`, `status` (`active`/`removed`), `removed_at`, `merged_into` |

### Story graph (`0002_story_graph.sql`)
| Table | Purpose | Key columns |
|---|---|---|
| `entities` | Characters, places, organizations | `kind`, `name`, `description` |
| `entity_aliases` | Other names and forms (nicknames, inflected forms); the base of the name registry in the deterministic checks | `entity_id`, `alias` |
| `relationships` | Entity to entity, free-text kind | `from_entity_id`, `to_entity_id` (never equal), `kind`, `directed` |
| `timeline_events` | Events with the author's date text and manual order | `title`, `when_text`, `sort_order`, `scene_id`, `place_id` |
| `timeline_event_participants` | Who took part | `event_id`, `entity_id`, `role` |

### Canon ledger (`0003_canon_ledger.sql`)
| Table | Purpose | Key columns |
|---|---|---|
| `facts` | A statement about the story | `entity_id` (optional subject), `text`, `status`, `origin` (`author`/`ai`/`import`), `source_ref`, `stale`, `stale_reason`, `approved_by`, `approved_at` |
| `fact_evidence` | Supporting passages (at least one for explicit and AI facts, enforced by the API) | `fact_id`, `passage_id`, `text_hash` at citing time |
| `fact_status_history` | Every status change | `fact_id`, `from_status`, `to_status`, `changed_by`, `reason`, `changed_at` |

Fact statuses: `explicit` (stated in the text), `author_approved`, `ai_hypothesis`, `rejected` (the author refused a hypothesis; added to the three in the handoff so a refusal has somewhere to go). Rules in the schema:
- `author_approved` requires `approved_by` and `approved_at`, written only by the explicit approve call, so an AI hypothesis cannot become canon by a plain update.
- `stale_reason` is allowed only when `stale = 1`.
- Evidence and history rows must point at existing facts and passages.

## Rules enforced by the database
Foreign keys are on for every connection (`PRAGMA foreign_keys`); nothing cascades, so removing a parent row with children is refused. Enumerations, lengths, hash length and the passage and fact rules above are `CHECK` constraints. Tables are `STRICT`. The file uses WAL journaling and a 5-second busy timeout.

## Migrations
- Files `core/migrations/NNNN_name.sql`, applied in version order at startup; applied versions and checksums are kept in `_sqlx_migrations`. Editing an applied migration is detected and refused; fix by adding a new one.
- Forward-only: there are no down migrations. Back up the database before a release that changes the schema.
- Tests (`db::tests`): apply to an empty database; apply twice (no change); roll forward over a database that already holds data; opening a file keeps data; invalid rows are rejected and their valid counterparts accepted; Cyrillic text round-trips byte for byte.
